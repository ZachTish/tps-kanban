# TPS Kanban 0.2.2

## Intent

Make every Kanban checkbox/status operation use GCM's authoritative mapping contract without losing structurally valid tasks whose markers intentionally have no workflow mapping.

## Changes

- Removed Kanban's copied status/checkbox lookup table and local toggle/completion fallbacks. Display, grouping, filter resolution, drag/drop, source-line toggles, and root/card task creation consume only the exact ordered rows returned by GCM `taskCheckboxes` version 1; Kanban does not supplement missing default mappings.
- Preserved the difference between structure and workflow semantics. Any Markdown list item with one checkbox character remains a task even when its marker is unmapped, stays in discovery and bounded previews, and can participate in structural Kind, title, tag, authored custom-field, and custom-formula behavior.
- Unmapped structural tasks expose no derived workflow aliases (`task.status`, `checkboxStatus`, `open`, `done`, or `completed`). They fail workflow filters closed, appear in **Ungrouped** on status-grouped boards, render a disabled checkbox, and refuse status toggles/status-lane drops while still allowing non-workflow field and tag changes.
- Custom markers, aliases, alternate status markers, and uppercase `X` normalization follow the exact GCM result. Empty and multi-character checkbox tokens are malformed and are neither promoted to todo nor reclassified as bullets.
- Explicit or default task creation fails before any task-line write when the required status has no configured mapping or the capability is unavailable, malformed, incompatible, or throws. Unfiltered creation resolves its canonical todo intent through GCM instead of synthesizing `- [ ]` locally, and the captured mapping plus workflow ownership are revalidated inside the atomic update.
- Checkbox toggles capture the source and target meanings, then compare the expected marker and revalidate both mappings inside the atomic line update. Status drops re-read both mappings after confirmation and again at the atomic write boundary, then apply only to the captured exact line or one uniquely relocated identical line; mapping changes and changed or ambiguously duplicated sources produce zero note changes.
- Workflow checkbox writes remove the configured key and stale `status`, `taskStatus`, `task.status`, `task.checkboxStatus`, and `checkboxStatus` carriers explicitly owned by GCM. Nested relational values and closed inline-code examples are parsed safely, and the exact separately configured relational status field is preserved. Formula and card-style contexts scrub authored workflow/completion aliases before overlaying only canonical mapping-derived values.
- Completion classification uses only GCM's coherent done-status capability and never falls back to recurrence settings or a hardcoded status set. When completion authority is missing, malformed, or contradictory, mapped status remains available but completion-derived formulas/styles are omitted and open/done filters fail closed.

## Compatibility and migration

- Backward-compatible patch; no settings, Base, lane, note, task, or stored-data migration.
- Minimum supported Obsidian remains 1.10.0.
- TPS Global Context Menu 1.17.1 is required for status-driven synthesized-task operations. Native note rows remain independent.

## Validation

- Focused behavior covers exact custom mappings, aliases, alternate markers, strict bidirectional resolver validation, structural unmapped rows, stale authored-carrier scrubbing, absent workflow aliases, missing/contradictory completion authority, non-workflow filters/formulas, Ungrouped routing, capability load order/replacement, version mismatch, malformed and throwing providers, mapping/ownership races, stale/ambiguous exact-line compare-and-swap, relational-status preservation, status lanes, and fail-closed task creation.
- The complete declared Kanban suite, TypeScript, mandatory separate production-mode build, and reloaded test-vault UI verification are recorded before publication.
- Test runtime state is preserved. Production is not accessed.

## Known limitations

- Task creation and status-driven line mutations intentionally stop when GCM's mapping capability is unavailable or the requested/current status is unmapped. Structurally valid unmapped tasks remain visible and retain non-workflow interactions.
- When root-task creation must first create a brand-new destination note and the mapping changes before the guarded append, the stale task is prevented but the empty destination may remain. Kanban does not delete it because ownership cannot be proven safely across that cross-file interval.
- Formula-backed lanes remain read-only as documented in 0.2.0.
